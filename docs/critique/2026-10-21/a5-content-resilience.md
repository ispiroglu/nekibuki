# A5 — Content, States, Resilience & Performance

Target: Nekibuki, impeccable/integration @ a9952f7, http://localhost:5190
Method: isolated design review (Assessment A5), 390x844 light + dark, 320x568 spot-check (long names, short viewport), report/history/camera/profile routes, plus the shared `evidence` route matrix read (not re-run)
Layer score: 3/4
Nielsen: H2 Match between system and real world = 3/4, H9 Help users recognize, diagnose and recover from errors = 3/4, H10 Help and documentation = 2/4
Audit dimension: Performance = 3/4

Strengths:
- **Failure copy is specific and actionable everywhere I could break the app.** Camera permission denied shows "Camera access is off" + "Nekibuki needs the camera to look at the place in front of you." + a primary "Choose from gallery" button + a "How to enable the camera" disclosure with a *reload the page* / *try again* link inside the sentence (`src/screens/camera-screen.tsx:1086-1189`, screenshot `16-camera-permission-denied.png`). API failure during analysis shows "Could not reach the guide. Check your connection." with "Try again" and "Back to the camera" (`src/components/capture/analyzing-overlay.tsx:79-166`, screenshot `19-analyze-api-abort.png`). History load failure says "We couldn't load your places. Check your connection and try again." with a "Try again" button (`src/screens/history-screen.tsx:104-120`). No stack traces, no HTTP codes, no "unknown error" anywhere I found.
- **Empty states give the next action, not just the absence.** "Nothing yet — Point your camera at a monument, a landscape or a street corner and this is where it lives." + an "Open the camera" button; "No saved places yet — Tap the bookmark on a guide to keep it here." + "Show all places"; "No matches — Try another word, or clear the filters." + "Clear filters" (`src/screens/history-screen.tsx:122-168`, screenshot `22-history-no-match-390.png`, `11-places-saved-empty.png`). This is the standard most apps fail.
- **Report voice holds the product promise without inflating it.** "High confidence / Likely match / Best guess" instead of a percentage (`src/screens/report-screen.tsx:201-206`); the annotation hint "Tap the dots on your photo" auto-dismisses and is positioned below the lowest marker so it never masks a dot (`src/components/report/photo-hero.tsx:43-53,179-190`); the chat placeholder "Ask about Eiffel Tower…" and the suggested-question chips make the first question free (`src/components/report/chat-panel.tsx:107-127,205`).

Findings:

### [P1] Chat failure message misdiagnoses the cause and contradicts the toast
- Location: `src/components/report/chat-panel.tsx:155-168` (hardcoded inline copy) vs `src/components/report/chat-panel.tsx:91` (toast) and `src/lib/api.ts:105-112` (server message is parsed and discarded for the inline state).
- Evidence: I set `context.setOffline(true)` in a fresh 390x844 context, opened `/report/demo-eiffel`, tapped the "Ask about Eiffel Tower…" composer and sent "Who paid for the first ticket?". The chat log kept the question and appended a persistent bubble reading **"No answer — the guide could not reach the server."** with a "Try again" link, while the sonner toast above the sheet read **"Could not reach the guide. Check your connection."** — two different statements of the same failure (screenshot `13-chat-offline-error.png`). The inline string is a literal, so it is identical for every failure mode. The worker can return 401 with `{"error":"Your session expired. Sign in again."}` (`worker/index.ts:37,48`) and 400/413/415 messages; in those cases the toast shows the real cause while the inline bubble still accuses the network, and "Try again" cannot fix an expired session — there is no re-auth affordance in the sheet.
- Impact: Casey, whose connection drops in a basement or a lift, is told the server is unreachable when the real cause was a 4xx. Jordan, who reads the persistent bubble (the toast disappears in 4s), retries the same request indefinitely with no path to recovery. A user would plausibly contact support about this.
- Fix: store the `ApiError.message` alongside `{id, question}` in `failed` and render `error.message` in the inline bubble instead of the literal, and show a "Sign in again" action instead of "Try again" when `error.code` is `http_401`. Keep one sentence for one failure.
- Suggested command: /impeccable clarify

### [P1] No fallback when a photo fails to load — the report hero and every history thumbnail show a broken-image glyph
- Location: `src/components/report/photo-hero.tsx:110` and `src/screens/history-screen.tsx:215` (both `<img>` elements have no `onError`); `src/screens/history-screen.tsx:226-230` has a fallback branch, but it only fires when `previewUrl` is *empty*, not when the load fails.
- Evidence: In a fresh context I aborted every request matching `**images.unsplash.com/**` and opened `/report/demo-eiffel`. The hero became a flat grey field with a small broken-image icon in the top-left corner, **while the four numbered annotation dots and the "Tap the dots on your photo" pill stayed on screen pointing at nothing** (`naturalWidth: 0`, `complete: true`, hero box still 506px tall). Navigating to the Places panel showed the same broken glyph in all three 72px thumbnails, each row's title and date still correct (screenshots `14-report-image-abort.png`, `15-history-image-abort.png`).
- Impact: The product's whole promise is "the photo is the source". A first visit on a weak connection (the stated operating context) yields a report whose evidence is a browser error icon and a hint telling you to tap dots on a blank rectangle. It reads as a broken build, not a degraded state, and there is no retry.
- Fix: add `onError` to both images that swaps in the paper/muted block plus a quiet caption ("The photo could not be loaded. The guide below is still complete." / a Camera glyph for the row), and hide the annotation dots and the tap-the-dots hint when the hero image has failed to load. A `useState` flag on the hero is enough; no new dependency.
- Suggested command: /impeccable harden

### [P2] "Terms and Privacy Policy" is plain text and neither document exists in the product
- Location: `src/screens/login-screen.tsx:163-166`; `grep -rn "href=" src` returns **zero** results across the whole app; `public/` contains no terms or privacy file; there is no route for them.
- Evidence: The login footer reads "By continuing you agree to our Terms and Privacy Policy." with "Terms" and "Privacy Policy" rendered as ordinary text inside a `<p>`. Nothing in `src/`, `public/` or `worker/` contains a terms or privacy document, and no route renders one. The only other footer text in the app is "Nekibuki v0.1 · made for curious travellers" (`src/screens/profile-screen.tsx:216-219`), which is not a link either.
- Impact: This is the one piece of legal/consent copy in the product and it points at nothing. Jordan reads every word before tapping "Continue with Google"; Casey on a hotel wifi is asked to consent to an invisible document. It is also the clearest H10 gap: the app has no help, about or support surface of any kind.
- Fix: either link both names to real `/terms` and `/privacy` pages (one static page each, offline-cached by the service worker like the rest of the shell), or remove the sentence until the pages exist. If they stay, make them real links with `rel="noopener"` and a visible focus ring.
- Suggested command: /impeccable document

### [P2] The third panel is called History, Places and "your places", and its icon is a clock
- Location: `src/components/layout/page-dots.tsx:5-9` (`{ index: 2, label: 'Places', icon: History }`), `src/screens/history-screen.tsx:54` (`<h1>History</h1>`), `src/screens/camera-screen.tsx` hint "Swipe between camera, you and your places", `src/screens/history-screen.tsx:133-146` empty states, `src/screens/profile-screen.tsx:85,198` ("Places", "Clear my places").
- Evidence: The bottom pill's third button is announced as "Places" but draws lucide's **History** clock icon (screenshot `20-profile-longname-390.png`, bottom pill). Tapping it opens a screen titled **History** whose empty states say "Nothing yet" and "No saved places yet", while the camera hint calls the same panel "your places" and the profile stats call it "Places" (3 Places / 3 Cities). PRODUCT.md names the panels "You, Camera, Places".
- Impact: A traveller who was told the app keeps "your places" looks for a bookmark or a map, finds a clock, and lands on a screen called "History" — which in a photo product reads as a changelog. It is the single clearest mismatch between the system's language and the traveller's mental model, and it costs a search every time.
- Fix: pick one word. Given the icon and the empty-state copy, "Places" is the better name — rename the screen heading to "Places", keep the nav label "Places", and change the hint to "Swipe between the camera, your profile and your places". If "History" is preferred, change the icon to a bookmark and the empty states to "History".
- Suggested command: /impeccable clarify

### [P2] History row dates mix four formats in one column
- Location: `src/lib/utils.ts:12-26` (`formatRelativeDate`) consumed by `src/screens/history-screen.tsx:196-204,240`.
- Evidence: One seeded list renders as "Blue Mosque · Istanbul · **05:16 PM**", "Colosseum · Rome · **2 days ago**", "Eiffel Tower · Paris · **6 days ago**". The function returns `Just now` (<1 min), `N min ago` (<1 h), a **locale clock time** (same calendar day), `Yesterday`, `N days ago` (<7 days) and an **absolute date** (`Oct 13, 2026`) beyond 7 days. My 320x568 profile run with a 6-day-old row and the seeded 3-hour-old row in the same list (screenshot `15-history-image-abort.png`, `20-profile-longname-390.png`) confirms the two scales sit side by side; an 8-day-old row would render `Oct 13, 2026` under a "6 days ago" row.
- Impact: The column is the only ordering cue in the list; four formats make the reader re-parse each row, and the switch between a clock time and a relative day implies a different kind of fact (a time of day vs a distance in days) for the same field.
- Fix: one rule — "Today, 17:16" style for today, "Yesterday" for the previous day, "N days ago" up to 7, and "13 Oct" (no year) beyond that. That is four states with one axis (distance), which is what the column means.
- Suggested command: /impeccable clarify

### [P3] The service worker precaches ~68 KB gzip of assets the browser never fetches
- Location: `vite.config.ts:41-67` (workbox `globPatterns`), built output `dist/sw.js` (read-only inspection of `/Users/xpirr/orca/workspaces/nekibuki/impeccable-integration/dist`).
- Evidence: The generated `sw.js` precache list includes `assets/dist-C1g6JUNG.js` (213 KB raw / **54.5 KB gzip**, the Supabase client — `grep supabase` matches GoTrueClient/createClient) and `assets/newsreader-vietnamese-wght-normal-*.woff2` (12 KB) and `newsreader-latin-ext-*.woff2` (36 KB). None of the three are fetched by the browser: Supabase is behind `import('@supabase/supabase-js')` (`src/lib/supabase.ts:22`) so it is a lazy chunk, and the font subsets are gated by `unicode-range` — my resource log for `/report/demo-eiffel` shows only `newsreader-latin-wght-normal.woff2` (58 KB) requested, once, at t=400 ms. The service worker still downloads and stores all three at install.
- Impact: Every first visit pays ~68 KB gzip of install-time download for code and glyphs the traveller will never load, on the connection the product assumes is poor. It is invisible to `performance.getEntriesByType('resource')` because the SW fetches happen outside the page, which is exactly why it is worth stating.
- Fix: exclude `assets/dist-*.js` and the `newsreader-vietnamese-*`/`latin-ext-*` subsets from `globPatterns` (or move them to a runtime cache), and add the Supabase chunk back only when `VITE_AUTH_MODE=supabase`.
- Suggested command: /impeccable optimize

Minor observations:
- The top-center sonner toast sits at `offset: 20` and covers the report's floating action row (back / save / share / delete) when it fires over the sheet — visible in `13-chat-offline-error.png`. On the report screen the toast should be pushed below the 44px action row or anchored bottom.
- `src/components/capture/analyzing-overlay.tsx:85-90` paints the full camera frame again as a `scale-110` `blur-2xl` (24px) full-screen layer behind the modal, for the entire 3–8 s analysis. On a mid-range phone that is a large blur over a ~2560×1440 decode while the GPU is also drawing the sheet.
- The capture path encodes the frame three times on the main thread: `captureVideoFrame` (JPEG q0.92 at camera resolution) → `compressImage` (re-decode + re-encode at 1800px/q0.86) → `createPreviewDataUrl` (720px/q0.72 thumbnail). `src/lib/image.ts:96-113`, `src/screens/camera-screen.tsx:378`.
- `manifest.webmanifest` ships a single `theme_color: "#faf9f5"` (paper) while `index.html` correctly ships media-scoped light/dark theme-colors. In dark mode the installed PWA's splash and task-switcher strip stay paper-coloured.
- The analysing overlay's own copy rotates every 1.6 s between messages (`ANALYZING_MESSAGES`) while a `(12s)` counter ticks; on a slow connection the elapsed counter is the only honest signal, which is good, but the rotating line is decorative noise next to a real wait — it is `aria-hidden` on screen and duplicated for screen readers, which is correct.
- Direct navigation to `/report/demo-eiffel` in a cold browser (before the app shell at `/` has seeded the demo records) lands on "This guide is gone — It may have been deleted from this device." (`src/screens/report-screen.tsx:186-198`); the demo data is seeded by `Shell` (`src/components/layout/shell.tsx:52`). For a real traveller opening a shared link on a new device the message is also wrong — the guide is not on this device yet, it is not deleted.

Persona red flags:
- **Jordan (First-Timer)**: "Terms and Privacy Policy" on the login screen is not a link and neither document exists anywhere in the app — Jordan reads it, tries to open it, finds nothing, and has no way to learn what they agreed to before tapping "Continue with Google". Second red flag: the profile row "Language / Language of the guide" (screenshot `20-profile-longname-390.png`) is the app's only clue that EN/TR changes the *guide* and not the interface, and it repeats the word "Language" instead of saying what changes; Jordan cannot tell whether tapping "TR" translates the button they are looking at.
- **Casey (Distracted Mobile User)**: on a dropped connection mid-question, the chat panel shows "No answer — the guide could not reach the server." with a "Try again" link and a separate toast reading "Could not reach the guide. Check your connection." (screenshot `13-chat-offline-error.png`) — two contradictory diagnoses for one failure, and the persistent one asks Casey to retry a request that is not the problem when the cause is an expired session. Casey is standing in the street, one-handed, and the app offers no path forward beyond repeating a failed tap.

Questions:
- If the photo is the source, what should the report look like when the photo cannot be fetched — and should the app open a photo-first guide at all when it has no photo to show?
- Can a traveller tell, from any screen, that the interface is English and only the *guide* can be Turkish? Right now "Language / Language of the guide" is the entire explanation.
- Would you rather the third panel be called "History" (matching the clock icon a traveller sees) or "Places" (matching the product promise and the profile stats)? The app currently asserts both, and the traveller has to guess which one is real.

Not exercised / limits of this layer:
- **Service worker and offline shell were not exercised in a browser**: `vite.config.ts:68` sets `devOptions: { enabled: false }`, so the dev server on :5190 registers no worker. I inspected the built output read-only at `/Users/xpirr/orca/workspaces/nekibuki/impeccable-integration/dist` (`sw.js`, `registerSW.js`, `manifest.webmanifest`, `index.html`, `_headers`) and confirmed: precache + `navigateFallback: /index.html` with `/api/` denied, CacheFirst for `images.unsplash.com`, StaleWhileRevalidate for Supabase storage, strict CSP, immutable asset cache headers, light/dark `theme-color` media queries. No install or offline navigation was actually run.
- **Network timings were measured against the Vite dev server**, which serves unbundled ESM (lucide-react 5.2 MB, react-dom 3.1 MB, motion 2.1 MB, react-router 1.4 MB as raw module responses). Those numbers are not production-representative and are excluded from the Performance score; production figures come from the built `dist` (≈265.6 KB gzip JS across 12 chunks, 12.3 KB gzip CSS, ≈196 KB gzip on the first-paint critical path incl. two modulepreloads).
- **LCP was not captured**: `performance.getEntriesByType('largest-contentful-paint')` returned nothing in this Chrome build. Recorded instead: FCP 420 ms (dev), CLS **0** (buffered `layout-shift` observer), hero image request start t=759 ms, duration 35 ms, transfer 60 255 B, `srcset` 640/960/1280/1600 + `sizes="100vw"`, browser chose the 960w candidate for the 390 CSS px / DPR 2 slot, `decoding="async"`, no `loading="lazy"` on the LCP element (correct).
- **The real vision provider was never exercised**: the shared API on :8787 served the deterministic mock, so the Gemini-specific error copy was read from `worker/services/gemini.ts` source only. The worker-side message "Send the photo as multipart/form-data." (`worker/index.ts:70`) is the one piece of jargon in the error surface, but it is only reachable if the client sends the wrong content type.
- **The camera was judged on HUD, copy and state only**; the fake device produced a live-looking frame, so no judgement is offered on photo quality. Long-name and short-viewport checks used a synthetic 57-character name in the demo user record; the profile `h1` truncates cleanly (`scrollWidth` 809 vs `clientWidth` 200 at 320 px, document `scrollWidth` 320 = `clientWidth`), so no overflow occurs.

SUMMARY: 3/4; 0 P0, 2 P1, 3 P2, 1 P3; the chat failure state misdiagnoses non-network errors and the photo has no load-failure fallback, so a degraded report renders as a broken image instead of a guide.
